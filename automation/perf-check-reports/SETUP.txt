===============================================================================
 PERF CHECK REPORTS - SETUP
 Several VMs (e.g. 3 VMs x 3 instances, Always On AGs), primary instances only,
 one email with one report file per VM, run by ONE SQL Agent job.
 Files: automation/perf-check-reports/powershell  (+ database_mail_setup.sql)
===============================================================================

Accounts:
  - SQL login dba_perfcheck .... ONLY for connecting to the instances (collecting data)
  - EMEA\Admin.partner.db ...... everything else: runs PowerShell / the Agent job,
                                 writes the files, reads the other VMs' services,
                                 sends the email
The dba_perfcheck password is saved encrypted (Windows DPAPI) so that ONLY
EMEA\Admin.partner.db, on the coordinator, can decrypt it.

-------------------------------------------------------------------------------
 1. CHOOSE THE COORDINATOR AND COPY THE FILES
-------------------------------------------------------------------------------
Pick ONE SQL instance with SQL Agent to run the job (the coordinator).

From the repo folder automation/perf-check-reports/powershell, copy to e.g.
C:\DBA\PerfCheck on the coordinator:

    Invoke-PerfCheck.ps1
    PerfCheck.sql
    Run-PerfCheck.bat              (to save the password, step 4)
    Run-PerfCheck-Agent.bat        (used by the job)
    servers.example.txt        ->  save as servers.txt

CreateAgentJob_PerfCheck.sql and database_mail_setup.sql are only opened in
SSMS; they don't have to be on that disk.

-------------------------------------------------------------------------------
 2. SQL LOGIN dba_perfcheck ON ALL 9 INSTANCES
-------------------------------------------------------------------------------
Every instance must allow SQL authentication (mixed mode):

    SELECT SERVERPROPERTY('IsIntegratedSecurityOnly');   -- 0 = mixed mode

Run the SETUP block at the top of PerfCheck.sql on EVERY instance, including
secondaries, as sysadmin, with a strong password (CHECK_POLICY = ON).
On AG replicas create it with the SAME SID everywhere (shown in the block), so it
keeps working after a failover.

The login gets only: VIEW SERVER STATE, VIEW ANY DEFINITION, ALTER SETTINGS,
ALTER ANY EVENT SESSION, msdb read + DatabaseMailUserRole, EXECUTE on xp_readerrorlog.
  - ALTER SETTINGS is the broadest one (it allows changing any server setting).
    It's only used to lower 'blocked process threshold' during the window and put
    it back. Leave it out to be safer: the check still runs, but blocking is then
    captured only if the threshold is already set on that instance.
  - Never make it sysadmin.

-------------------------------------------------------------------------------
 3. EMEA\Admin.partner.db ON THE COORDINATOR
-------------------------------------------------------------------------------
a) Folder: MODIFY rights on C:\DBA\PerfCheck (it writes Reports\, Logs\ and the
   saved password file).
b) Windows right "Log on as a batch job" - probably needed to run as an Agent
   proxy (not confirmed - check this if the job step doesn't start).
c) Windows login on the COORDINATOR instance only, to send the email with the
   files attached (Database Mail doesn't allow attachments for SQL logins):

    USE master;
    IF SUSER_ID(N'EMEA\Admin.partner.db') IS NULL CREATE LOGIN [EMEA\Admin.partner.db] FROM WINDOWS;
    USE msdb;
    IF USER_ID(N'EMEA\Admin.partner.db') IS NULL CREATE USER [EMEA\Admin.partner.db] FOR LOGIN [EMEA\Admin.partner.db];
    ALTER ROLE DatabaseMailUserRole ADD MEMBER [EMEA\Admin.partner.db];

   (No SQL Server rights are needed on the other 8 instances: data is collected
    with dba_perfcheck.)
   No Windows login at all? Set SmtpServer in step 5 instead and
   MailWindowsAuth = $false.
d) SSIS / SSRS / SSAS service state of the other 2 VMs is read over CIM / WinRM
   as this account (remote management rights on those VMs). Not allowed? Set
   RemoteBiServices = $false in step 5.

-------------------------------------------------------------------------------
 4. DATABASE MAIL ON THE COORDINATOR
-------------------------------------------------------------------------------
Run database_mail_setup.sql on the coordinator instance with @MaxFileSizeMB = 10
(a report covering 3 instances can be bigger than the default limit of about 1 MB).

-------------------------------------------------------------------------------
 5. CONFIG
-------------------------------------------------------------------------------
servers.txt - one INSTANCE per line, instance names, not listeners:

    SQLVM1\INST1
    SQLVM1\INST2
    SQLVM1\INST3
    SQLVM2\INST1
    ...
    SQLVM3\INST3

If SQL Browser is blocked, add the port, e.g. SQLVM1\INST1,1433

$Config at the top of Invoke-PerfCheck.ps1:
    Recipients            = 'dba-team@yourcompany.com'   (and CopyRecipients if needed)
    MailProfile           = the profile from database_mail_setup.sql
    IncludeLocalInstances = $false
    PrimaryOnly           = $true      (or pass -PrimaryOnly)
    SqlLogin              = 'dba_perfcheck'
    SqlAuthOnly           = $true      instances ONLY with the SQL login, never Windows
    CredentialScope       = 'CurrentUser'   only the saving account can decrypt it
    MailWindowsAuth       = $true      email as EMEA\Admin.partner.db (attachments)
    MailInstance          = 'SQLVM1\INST1'  the coordinator instance (example)
    Encrypt               = $true      optional: encrypt the connections
    RemoteBiServices      = $false     only if WinRM to the other VMs isn't allowed
    SmtpServer            = only if Database Mail can't be used

-------------------------------------------------------------------------------
 6. SAVE THE dba_perfcheck PASSWORD - AS EMEA\Admin.partner.db
-------------------------------------------------------------------------------
On the coordinator, open a command prompt AS the account that runs the job:

    runas /user:EMEA\Admin.partner.db cmd
    cd /d C:\DBA\PerfCheck
    Run-PerfCheck.bat -PrimaryOnly -NoPerf -Label TEST

It asks for the dba_perfcheck password -> enter it -> answer Y to save it.
It is saved as C:\DBA\PerfCheck\PerfCheck.EMEA_Admin.partner.db.cred:
  - encrypted with Windows DPAPI for EMEA\Admin.partner.db on this VM only
    (no other account can decrypt it; a copy of the file is useless elsewhere)
  - NTFS: only Administrators, SYSTEM and EMEA\Admin.partner.db
  - decrypted only into memory (SecureString) when the check runs; never written
    to a connection string, the log or job history
  - change it later: Run-PerfCheck.bat -ResetCredential (as the same account)
What it can't prevent: an administrator on the coordinator, or anything running
as EMEA\Admin.partner.db, can recover it. Hence the minimal rights in step 2.

That same run is the first test. Check:
  - ONE email arrives with 3 attachments (one .html per VM)
  - ConnectedAs shows "SQL: dba_perfcheck" for every instance
  - secondary-only instances are listed as skipped
  - AG tables show only the AGs where that instance is primary

Then a short performance window:

    Run-PerfCheck.bat -PrimaryOnly -SampleSec 10 -DurationMin 2 -Label TEST

On every instance, nothing left behind:

    SELECT value_in_use FROM sys.configurations WHERE name = 'blocked process threshold (s)';
    SELECT name FROM sys.dm_xe_sessions WHERE name = 'DBA_PerfWindow';   -- no rows

-------------------------------------------------------------------------------
 7. PROXY AND JOB (ON THE COORDINATOR)
-------------------------------------------------------------------------------
    USE master;
    CREATE CREDENTIAL [PerfCheckCred] WITH IDENTITY = N'EMEA\Admin.partner.db', SECRET = N'<its Windows password>';
    USE msdb;
    EXEC dbo.sp_add_proxy @proxy_name = N'PerfCheckProxy', @credential_name = N'PerfCheckCred', @enabled = 1;
    EXEC dbo.sp_grant_proxy_to_subsystem @proxy_name = N'PerfCheckProxy', @subsystem_name = N'CmdExec';

Open CreateAgentJob_PerfCheck.sql, set the values at the top and run it:

    @ScriptFolder = N'C:\DBA\PerfCheck'
    @Arguments    = N'-PrimaryOnly -Label SCHEDULED'
    @ProxyName    = N'PerfCheckProxy'
    @Schedule, @StartTime, and optionally @NotifyOperator

Start it once:

    EXEC msdb.dbo.sp_start_job @job_name = N'DBA - Health & Performance Check (all VMs)';

With the defaults the job runs about 31-35 minutes. Where to look:
  - SQL Agent job history
  - C:\DBA\PerfCheck\AgentJobStep_output.txt   (output of the last run)
  - C:\DBA\PerfCheck\Logs\                     (full log of each run)
  - C:\DBA\PerfCheck\Reports\                  (the .html reports)

-------------------------------------------------------------------------------
 IF SOMETHING GOES WRONG
-------------------------------------------------------------------------------
Job fails at once: "No saved SQL login for EMEA\Admin.partner.db"
    -> step 6 wasn't done as EMEA\Admin.partner.db (the file name shows the account).
Job log: "Saved SQL login ... could not be read"
    -> under the Agent proxy the account's user profile may not be loaded, which
       DPAPI CurrentUser needs. Fallback: CredentialScope = 'LocalMachine',
       CredentialReaders = @('EMEA\Admin.partner.db'), then save it again with
       Run-PerfCheck.bat -ResetCredential (as EMEA\Admin.partner.db). Then any
       account on this VM that can read PerfCheck.cred could decrypt it; the NTFS
       permissions are the guard.
Email has only a summary, no attachments
    -> the step output says why: usually EMEA\Admin.partner.db has no login /
       DatabaseMailUserRole on the coordinator (step 3c), or a file is above
       MaxFileSize (step 4).
An instance shows FAILED
    -> dba_perfcheck missing / wrong password / mixed mode off on that instance,
       or firewall / named-instance port between the coordinator and that VM.
Job step fails with exit code 3 or 4
    -> read the newest file in Logs\. (3 = script error, 4 = no email sent.
       0, 1 and 2 count as success: the email went out.)
